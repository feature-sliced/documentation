Слой `entities` в Feature-Sliced Design относится к нижним слоям и предназначен прежде всего для бизнес-логики. К нему могут обращаться все слои, кроме `shared`. Из-за такой широкой доступности изменения в `entities` могут затронуть многие части приложения. Поэтому этот слой нужно тщательно проектировать, чтобы избежать дорогостоящего рефакторинга.

Избыточные сущности усложняют определение того, какой код относится к этому слою, повышают связанность и заставляют постоянно решать, что откуда импортировать, поскольку код оказывается разбросан по соседним сущностям.

## Как поддерживать порядок в слое `entities`

### 0. Подумайте, можно ли обойтись без слоя `entities`

Может показаться, что без этого слоя приложение не будет соответствовать Feature-Sliced Design, но отсутствие слоя `entities` вполне допустимо. Это никак не нарушает правила FSD. Напротив, архитектура становится проще, а слой `entities` можно добавить позже, когда потребуется масштабировать приложение. Например, если ваше приложение работает как тонкий клиент, этот слой ему, скорее всего, не нужен.

<Aside title="Что такое толстые и тонкие клиенты?">

Различие между _толстыми_ и _тонкими клиентами_ связано с тем, как приложение обрабатывает данные:

- _Тонкие_ клиенты полагаются на сервер при обработке большей части данных. Бизнес-логика на стороне клиента минимальна и сводится к обмену данными с сервером.
- _Толстые_ клиенты выполняют значительную часть бизнес-логики на стороне клиента, поэтому слой `entities` может быть им полезен.

Приложение не обязательно относится только к одному из этих типов. Разные части одного приложения могут работать как «толстый» или «тонкий» клиент.

</Aside>

### 1. Избегайте преждевременного выделения слайсов

В отличие от предыдущих версий, FSD 2.1 рекомендует откладывать декомпозицию на слайсы, а не проводить её заранее. Это относится и к слою `entities`. На первых этапах можно разместить весь код в сегменте `model` страницы, виджета или фичи, а к рефакторингу вернуться позже, когда бизнес-требования устоятся.

Помните: чем позже вы переносите код в слой `entities`, тем меньше рисков при последующем рефакторинге. Код этого слоя может влиять на работу любого слайса на вышележащих слоях.

### 2. Не создавайте лишние сущности

Не создавайте отдельную сущность для каждого фрагмента бизнес-логики. Вместо этого используйте типы из `shared/api`, а логику размещайте в сегменте `model` текущего слайса. Бизнес-логику, которая нужна в нескольких местах, размещайте в сегменте `model` слайса сущности, оставляя определения данных в `shared/api`:

<FileTree>
- entities
  - order
    - index.ts
    - model
      - apply-discount.ts Бизнес-логика, использующая OrderDto из shared/api
- shared
  - api
    - index.ts
    - endpoints
      - order.ts
</FileTree>

### 3. Не размещайте CRUD-операции в сущностях

CRUD-операции необходимы, но часто представляют собой шаблонный код без существенной бизнес-логики. В слое `entities` такой код может создавать лишний шум и мешать находить важную логику. Вместо этого размещайте CRUD-операции в `shared/api`:

<FileTree>
- shared
  - api
    - client.ts
    - index.ts
    - endpoints
      - order.ts Все CRUD-операции, связанные с заказами
      - products.ts
      - cart.ts
</FileTree>

Для сложных CRUD-операций, например атомарных обновлений, откатов или транзакций, оцените, подходит ли слой `entities`. Используйте его с осторожностью.

### 4. Храните данные аутентификации в `shared`

Для данных аутентификации, например токенов или пользовательских DTO, полученных от сервера, лучше использовать слой `shared`, а не создавать сущность `user`. Эти данные привязаны к конкретному контексту и вряд ли понадобятся за пределами аутентификации:

- Ответы на запросы аутентификации, например токены или DTO, часто не содержат полей, необходимых для более широкого использования, или различаются в зависимости от контекста, например для приватного и публичного профилей пользователя.
- Хранение данных аутентификации в сущностях может привести к импортам между слоями, например из `entities` в `shared`, или к использованию `@x` нотации, что усложняет архитектуру.

Вместо этого храните данные аутентификации в `shared/auth` или `shared/api`:

<FileTree>
- shared
  - auth
    - use-auth.ts Данные аутентифицированного пользователя или токен
    - index.ts
  - api
    - client.ts
    - index.ts
    - endpoints
      - order.ts
</FileTree>

Подробнее о реализации аутентификации читайте в [руководстве по аутентификации](/ru/docs/guides/examples/auth).

### 5. Сведите кросс-импорты к минимуму

FSD допускает кросс-импорты с помощью `@x` нотации, но они могут вызывать технические проблемы, например циклические зависимости. Чтобы избежать этого, проектируйте сущности в рамках изолированных бизнес-контекстов, устраняя необходимость в кросс-импортах:

Неизолированный бизнес-контекст (не рекомендуется):

<FileTree>
- entities
  - order
    - @x/
    - model/
  - order-item
    - @x/
    - model/
  - order-customer-info
    - @x/
    - model/
</FileTree>

Изолированный бизнес-контекст (рекомендуется):

<FileTree>
- entities
  - order-info
    - index.ts
    - model
      - order-info.ts
</FileTree>

Изолированный контекст объединяет всю связанную логику, например работу с позициями заказа и данными покупателя, в одном модуле. Это снижает сложность и защищает тесно связанную логику от изменений извне.
